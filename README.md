# 训练计划生成器

根据训练目标、可用器械和**训练历史**，生成今天该练什么的计划。

## 它解决什么问题

健身的人有两个反复出现的困扰：

1. **不知道今天该练哪个部位** —— 昨天练了胸，今天还能练胸吗？
2. **记不住上次练了多少** —— 卧推上周是 60kg 还是 65kg？（**尚未实现，见「已知限制」**）

这个工具把「今天练什么」变成一条命令，并且会参考历史记录，不会让你连续两天练同一个部位。

## 怎么跑起来

```bash
# 1. 创建虚拟环境
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # macOS / Linux

# 2. 装依赖
pip install openai python-dotenv streamlit

# 3. 配置密钥
copy .env.example .env
# 编辑 .env，填入 DEEPSEEK_API_KEY

# 4. 初始化数据库和动作库
python db.py
python seed_exercises.py
python seed_extra.py

# 5a. 网页版
streamlit run app.py

# 5b. 命令行版
python main.py
```

## 用法

```bash
python main.py                    # 生成计划，不保存
python main.py --save             # 生成并写入训练历史
python main.py --pattern legs     # 强制指定练腿
python main.py --help             # 查看帮助
```

## 项目结构

| 文件 | 职责 |
|---|---|
| `db.py` | 数据库连接与建表 |
| `schema.sql` | 两张表的定义 |
| `seed_exercises.py` | 动作库种子数据（69 条，健身房为主） |
| `seed_extra.py` | 补充 16 条自重动作，让「家里（自重）」场景可用 |
| `planner.py` | 核心逻辑：定分化 → 筛动作 → 拼 prompt → 调模型 → 校验 |
| `app.py` | Streamlit 网页界面 |
| `main.py` | 命令行入口 |

## 关键设计

**1. PPL 分化**

用户每周练 5–6 次，采用推（push）/ 拉（pull）/ 腿（legs）三循环。生成前先查最近两天的记录，推出今天该练哪个，避免连续练同一肌群。

**2. 模型只能在候选里选**

先用 SQL 从动作库筛出 12–15 个真实存在的动作，只把这些给模型。模型爱编造不存在的动作（比如「史密斯反向蝴蝶夹胸」），限制它的选择范围是可控性的前提。

**3. 入库前校验**

模型返回的每个动作名都必须在候选列表里，不在就重试。脏数据一旦入库，清理成本是入库前的十倍。

**4. 器械约束落在 SQL 上，不靠 prompt**

用户选「家里（哑铃）」时，`candidates()` 直接用 `WHERE equipment IN ('哑铃','自重')` 筛库。曾经只把「家里只有哑铃」写进 prompt，结果模型照样排了杠铃划船——因为它只能从候选里挑，而候选里本来就有杠铃动作。

能落到 SQL 的约束，永远不要指望 prompt 遵守。

**5. 不用向量库**

动作只有 85 条，输入是「肌群 + 器械」这种精确条件，`WHERE` 就够了。加向量检索属于过度设计：多装依赖、多一个故障点，准确率还不如 SQL。

## 数据结构

两张表职责分开：

- `exercises` —— 静态字典（动作名、肌群、器械、难度、分化、替代动作），只读
- `sessions` —— 动态记录（日期、动作、组数、次数、重量），每次训练新增

动作库像词典，训练历史像日记。合成一张表会导致查询混乱，且渐进超负荷无法计算。

## 已知限制

- **渐进超负荷尚未实现**：`last_weight()` 已写但未接入 prompt，生成的计划里重量恒为 0，用户需自己填。这是下一步要做的第一件事
- 单用户，没有账号体系
- 「写入训练记录」是可选勾选，忘记勾会导致下次分化判断缺数据
- 生成过程中按钮未禁用，连点会重复调用模型（重复付费）
- 动作库 85 条，不追求穷尽；弹力带动作尚未收录，所以选项里不提供
- 没有动作演示图或视频
